# 网关开机恢复与就绪判定

## 网页可访问不等于 QQ 已登录

QQ 网关通常包含多个独立状态：

1. WebUI / noVNC 进程已启动。
2. 官方 QQ 客户端已启动。
3. 机器人账号已完成登录。
4. OneBot HTTP 已开启且认证有效。
5. OneBot WebSocket 已开启，Core 的真实订阅已连接。
6. SocialRuntime 可以接收消息并完成模型及出站处理。

仅检查管理页面 HTTP 200，会漏掉“QQ 仍在登录页，OneBot 端口尚未监听”的情况。Console / Docker 健康状态不应被解读为所有聊天功能都正常。

## 推荐的启动顺序

- 首先确认持久化存储真实挂载，避免在空挂载点上启动新数据库或空登录目录。
- 启动现有网关及其所需的独立网络环境；保留原有 QQ 登录数据，不启动第二个生产 Gateway。
- 等待受认证的 `get_status` 返回 online，以及 `get_login_info` 与预期机器人账号一致。WebSocket 端口可达只是前置条件，真正的认证与订阅结果以 Core 为准。
- 再启动 Core，等待数据库与应用健康检查完成，然后启动该实例自己的入口服务。
- 共享反向代理由其独立运维流程管理，不通过机器人 Compose 操作其他项目。

等待必须有上限、脱敏错误状态和人工恢复入口。超时、认证失败或账号不符不能伪装成就绪。不要通过关闭认证、无限重启或增加第二个 OneBot 消费者来“修复”启动失败。

本版本 `SocialRuntime.start()` 的初次 OneBot 连接失败会使启动失败，尽管网关 Adapter 自身有重连调度。部署编排必须考虑这一实际行为，不能假定 Core 退出后 Adapter 仍会后台重连。本文未改变该 Java 行为，也不宣称已经实现无需人工介入的所有重启恢复情形。

## 官方客户端自动登录

如需重启后自动恢复，应由管理员明确同意，在官方 QQ 客户端配置其支持的自动登录能力。它涉及客户端保存登录信息，不能擅自开启，也不能把账号密码写入 Compose、启动参数、日志或公开仓库。

自动登录并不能保证绕过平台的手机确认、验证码或安全验证。出现这些要求时，应通过官方界面人工完成。保留 localhost 管理入口和 SSH 隧道，避免将 noVNC / 管理接口暴露到公网。

## 无回复时的排查顺序

- 检查主机 / Docker 是否重启，以及 Core 是否仍运行，先确认是否发生整个服务退出。
- 分别核对 QQ 登录态、OneBot HTTP 认证、WebSocket 订阅、SocialRuntime 状态。
- 再核对当前入站的权限、唤醒、模型请求、工具执行和出站结果；不要把网关离线误认为人格或表情功能失效。
- 保留持久化 Ledger、消息去重和 UNKNOWN 不盲目重发保护；恢复服务不等于重新执行历史失败工具。
- 通过新消息做少量真实私聊 / 群聊验收，区分后台配置检查与最终 QQ 收到回复。

实际重启验收应在授权维护窗口进行。安装启动等待脚本、使用模拟状态测试，以及当前在线探测通过，均不能替代一次尚未执行的完整主机重启测试。

所有示例仅描述通用部署原则，不包含私人配置、登录态、账号或凭据。
