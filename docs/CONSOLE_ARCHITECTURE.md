# Admin Console architecture — Phase 4B-1

## 时间筛选契约

Memory 筛选的浏览器 `datetime-local` 表示管理员本地时间，序列化为带 `Z` 的 UTC ISO-8601 Instant；后端 `Instant.parse` 校验，数据库采用 `[from,to)`。产品不改变服务时钟或管理员时区。测试以同一次捕获时间生成相对窗口，避免固定截止日期跨午夜排除新记录。

## 请求、失败状态与可访问性边界

所有管理 mutation 复用现有 api helper。CSRF token 只在模块内存中缓存；并发发现去重、超时/取消清理、401/403 及退出登录失效，不自动重放写操作。字段错误关联对应控件；错误文案由 HTTP 状态本地化，不展示后端异常。诊断新请求清除旧结果并避免旧响应覆盖；Logs 请求失败不等同成功空列表。

导航只包含实际实现页面；Agent/Groups 的既有能力分别归属 Persona/Simulation/Social Settings/Models/Conversations 与 Conversations/People/Access，不提供独立占位入口。对话框命名、描述、初始焦点、Tab 约束、Esc 与回焦构成一致交互契约；宽表格仅在自身容器内滚动。图表提供文本/表格替代，状态有文字而非仅颜色。

用户生成内容使用 React 文本节点和受控表单，不提供 HTML/Markdown 执行入口。浏览器持久化仅存 theme/language。安全响应包含 nosniff、DENY frame 和 no-referrer；Cookie 的 HttpOnly/SameSite/Secure 使用同一有效配置。CSP 暂缓：现有 SPA 的动态图表样式与资源连接尚未完成可部署策略审计，不在 closure 中以未经验证策略破坏管理功能；这不构成公网部署授权。

## Serving and frontend build

The Console is a React + strict TypeScript single-page application built with Vite. Its output is generated under `build/generated-resources/frontend` and becomes Spring Boot resources; `bootJar` depends on the separately invocable `frontendBuild` task. The frontend task uses Node v24.19.0 / npm 11.17.0; Java `test` does not depend on Node/npm. The checked-in npm lockfile fixes the frontend dependency graph. The browser has no direct integration adapter: it talks only to authenticated XingChen APIs.

## Authentication and sessions

Set `XINGCHEN_CONSOLE_ADMIN_USER` and a high-entropy `XINGCHEN_CONSOLE_ADMIN_PASSWORD` (14–72 UTF-8 bytes due to BCrypt's input bound) on first startup. The bootstrap runner stores only a BCrypt hash (Spring Security encoder, cost 12) in SQLite. BCrypt is chosen over Argon2id here to avoid adding a native/BouncyCastle dependency to this small Java baseline; it remains a mature, salted password hash. The values are not returned or logged. If no admin is bootstrapped, `/api/**` remains locked and the local service can still start for tests/maintenance; a remote bind fails closed unless the remote-bind opt-in and bootstrap credentials are configured.

Spring Security issues an opaque, server-side servlet session. Login rotates the session ID; logout invalidates the server-side session. The cookie is HttpOnly, SameSite=Strict, path `/`, with a 30-minute inactivity timeout. Set `XINGCHEN_PUBLIC_BASE_URL=https://...` or explicitly set `XINGCHEN_CONSOLE_COOKIE_SECURE=true` when HTTPS terminates at a trusted proxy; the Console does not terminate TLS. Restarting the process invalidates in-memory sessions.

CSRF uses Spring Security's cookie token repository. The XSRF cookie and response token are HttpOnly/JSON respectively; the same-origin SPA obtains the current token from `/api/auth/csrf` and keeps it in module memory only, never in browser storage or a URL. Login, config mutations, and logout require a token. The session cookie is HttpOnly and SameSite=Strict.

## Login throttling and proxy policy

Login failures are limited to five attempts per remote socket address and normalized username per ten-minute window. The limiter uses `HttpServletRequest.getRemoteAddr()` and does not trust arbitrary `X-Forwarded-For`, `Forwarded`, or `X-Forwarded-Proto`. Forwarded-header handling is disabled. `XINGCHEN_TRUSTED_PROXIES` is modeled as an explicit list for a future trusted-proxy resolver; this Phase does not consume client-supplied forwarding headers. Configure trusted TLS termination with `XINGCHEN_PUBLIC_BASE_URL`/cookie security explicitly.

## Bind and public URL

Default listener remains `127.0.0.1:3200`. Binding to a non-loopback address requires `XINGCHEN_CONSOLE_ALLOW_REMOTE=true` and bootstrap authentication credentials; otherwise startup fails. `XINGCHEN_PUBLIC_BASE_URL` is the explicit externally visible base URL used as HTTPS/security foundation. No reverse-proxy or DNS changes are part of this phase.

## API boundary and errors

`/health` is the only application health route left public and reports bounded service readiness fields. All `/api/**` management and existing read APIs require an authenticated session. This preserves the Phase 4A endpoint contract while moving it behind an authentication boundary. API errors return a safe `code`, message, and trace ID; Java stack traces are not returned to the UI. `ConsoleReadController` still omits secrets, cookies, tokens, prompts, and memory text except the legacy authenticated memory-reading API's explicitly scoped response.

## Gateway management contract (Phase 4B-2a)

`GatewayManagementPort` isolates the Console from gateway products. `SnowLumaGatewayAdapter` observes the existing OneBot v11 client only; the deterministic fake lives under the test profile. Official SnowLuma materials reviewed for this phase document QQ GUI QR login through Docker Framework noVNC (6081), SnowLuma WebUI management (5099), and OneBot HTTP/WS (3000/3001). They do not document a QR management API, an account-independent login-state API, or programmatic QQ logout/reconnect. XingChen therefore reports only DISABLED / CONNECTED / DISCONNECTED based on its integration configuration and OneBot transport; account identity is shown only after OneBot `get_login_info`. GUI-specific login states and QR lifecycle remain unsupported and are directed to the official UI. See `SNOWLUMA_GATEWAY_CONTRACT.md` for source details and version caveats.

Gateway endpoints are saved through `ConfigService` and immediately applied by reconfiguring the live OneBot client, without restarting the JVM. Loopback endpoints are accepted by default; a reviewed non-loopback endpoint requires the explicit application opt-in. Management UI origins allow HTTP(S) only and are opened directly by the browser, never fetched/proxied by XingChen. The OneBot client disables redirects. Token GET/status responses expose only configured booleans; token mutations use a private owner-only SecretStore outside SQLite, fail closed if restrictive permissions cannot be applied, and audit only action metadata. Session authentication and CSRF protect every mutation. The QQ bot account identity is a platform account and does not create a XingChen person membership.

## Config Service and audit

`ConfigService` owns the versionable Console/Runtime/Social/Model/Prompt/Access/Gateway category framework, validates server-side, writes approved non-secret values to SQLite, and emits a compact audit row (`timestamp`, actor, category, key, action). Gateway exposes OneBot HTTP/WS loopback endpoints, an external WebUI origin, enabled state, and token set/replace/clear. Secret status returns configured booleans only and stores no secret plaintext in SQLite. Gateway changes use `HOT_APPLY`; other runtime apply modes remain explicit (`RESTART_REQUIRED`, `EXTERNAL_RECONNECT_REQUIRED`) where appropriate.

## Bootstrap precedence and effective configuration (4B-5 blocker closure)

Environment/application.yml values are deployment defaults, not an override of explicit administrator state. `EffectiveConsoleConfiguration` loads a single immutable startup snapshot after database migrations. A saved `Console/publicBaseUrl` row wins over the deployment URL. Saving an empty string means **explicitly no public URL**, not "inherit environment". Saves remain `RESTART_REQUIRED`; the live cookie/posture snapshot changes only on restart. Both servlet cookie Secure and Security Center consume this snapshot. An explicit deployment cookie-Secure flag remains an independent hardening floor.

`FileSecretStore` is the effective credential source. An existing `.secret` is CONFIGURED even without metadata; `.cleared` is explicit absence and wins even if a secret file survived an interrupted Clear. Only a store with neither file may bootstrap from the environment. Replace installs an owner-restricted atomic secret and retires Clear; Clear durably installs the tombstone before deleting the secret. Subsequent bootstrap never resurrects a cleared credential. Files use owner-only POSIX permissions or Windows owner-only ACLs; unsupported secure storage fails closed.

OneBot HTTP and forward-WebSocket credentials use independent SecretStore keys and environment bootstrap names: `onebot-http-access-token` / `XINGCHEN_ONEBOT_HTTP_ACCESS_TOKEN`, and `onebot-ws-access-token` / `XINGCHEN_ONEBOT_WS_ACCESS_TOKEN`. A legacy `onebot-access-token` remains a read-only fallback only while a transport has not been explicitly initialized. Saving or clearing one transport initializes only that transport; a durable clear tombstone prevents fallback from silently restoring it. HTTP reads only the HTTP credential; the active forward-WebSocket reads only the WS credential. Neither value appears in configured/status responses or audit records. DeepSeek uses `XINGCHEN_DEEPSEEK_API_KEY`, then `DEEPSEEK_API_KEY`. The DSH adapter's actual launch credential is `DSH_LAUNCH_TOKEN`, bootstrapped into `dsh-launch-token`; the unrelated historical `DSH_API_KEY` is not reported as an effective launch credential.

Gateway mutations use the existing synchronous reconfigure path: disconnect the old transport, install a fresh credential snapshot and reconnect if enabled. `HOT_APPLY` means that credential/configuration is applied to new HTTP requests and the replacement WS connection, not a promise of successful remote authentication. In-flight requests/turns retain their original snapshots. Security Center's configured booleans are read from the same effective stores, never environment-variable presence. Bootstrap is system initialization, not a fabricated administrator audit action.

Evidence: `EffectiveConfigurationRestartTest` verifies actual Boot restart, servlet Cookie/posture consumers, Console API Replace/Clear, separate HTTP/WS values, fallback behavior, restart persistence, redacted status, and requests to a loopback fake. No live QQ integration is required or invoked.

## Overview and design system

Overview uses bounded subsystem flags and counters only; no QQ credentials, prompts, message bodies, or memory text are rendered there. Gateway status comes from `GatewayManagementPort`. Theme tokens are centralized in `frontend/src/ui/styles.css`. Light, dark, Wanning, and System preferences are stored locally; System maps only to light/dark. Primary interface strings use `zh-CN`/`en-US` catalogs and locale choice is stored locally. Responsive navigation becomes a drawer on narrow screens and honors reduced-motion preferences. Gateway page polls while visible, presents external login management honestly, and does not invent a SnowLuma QR/login API.

## Verification boundary

Backend and browser tests use temporary SQLite, loopback listeners, fake/disabled external integrations, and temporary credentials. They never connect to live QQ, SnowLuma, DSH, DeepSeek, or Zetu. E2E starts the produced bootJar on a discovered loopback port and tears down the JVM, browser and temporary database.

## Conversation Operations（Phase 4B-2b）

`ConversationConsoleService` is the bounded administrative read model. It aggregates conversation, membership, simulation state, cursor/unread summary, queue lane diagnostics, durable turn status, outbound UNKNOWN records, context lifecycle, DSH mapping and pending interaction counts. The UI never queries repositories or SQLite. Conversation identifiers in routes are parsed as UUIDs; platform conversation IDs remain data. List filters and sorting run server-side, with a maximum page size of 100 and a bounded page index. Since the current schema has no group-title record, group display uses the platform conversation ID; private display uses the latest safe member display/card name.

Members and recent-message APIs are paginated and bounded (maximum 100). Every response is `Cache-Control: no-store`; the browser does not persist conversation data in local storage. Message rendering returns a short text preview, sender/type/time and reply reference only. Raw OneBot metadata is inspected only to derive an allow-listed segment-kind summary and is never returned (including media URLs). Message text, prompts and memory content are excluded from logs and operation audit. Message read endpoints remain behind the authenticated session boundary.

Mutations are not repository writes from the controller. `ConversationConsoleService` calls `ConversationControlPort`, implemented by the serialized `SocialRuntime` lane. Mode and wake use an expected generation through `SimulationStateService` CAS. `CLOSED_AGENT` still checks the configured owner in a private conversation and the shared closed-agent policy; manual wake is owner-private only and cannot release WAIT. Reset calls `ConversationResetCoordinator` to cancel/fence the current generation, then queues the existing `SocialRuntime` reset cleanup (including transient DSH session retirement) on that same conversation lane. No reset endpoint deletes identity, alias, memberships, relationship, long-term memory or prompt-version rows. Stale operations return a conflict rather than overwriting newer state.

Every attempted mode, wake and reset operation produces a compact `conversation_console_audit` row with actor, conversation UUID, operation, bounded old/new summaries, result and timestamp. Error messages are static/safe; request content is not copied into audit. UNKNOWN outbound records are read-only and explicitly state that the system will not resend because delivery may already have succeeded. Interrupted turns show short IDs, execution state/time and fail-closed recovery notice; there is no retry endpoint. WAIT shows origin/generation/time/reason and is retired only through reset.

Context diagnostics distinguish current context estimate from cumulative usage and expose configured thresholds, current lifecycle, unread/recent counts, rollover/handoff summary and DSH mapping/pending counters only; full prompt, memory and session credentials are not returned. Deterministic conversation fixtures and their state-preparation endpoint are registered solely under `conversation-fake-e2e`, never in the default/production profile. Browser reload routes forward the SPA only for non-API, extension-free paths; missing API routes remain 404.

## People, Relationships, and Memory administration（Phase 4B-3a）

`PeopleMemoryConsoleService` is the authenticated, bounded read/write facade behind `/api/people`, `/api/relationships`, and `/api/memory`. People search is server-paged and matches stable platform user IDs, aliases, current display names and group cards. Person detail aggregates identity, alias history, memberships, relationship rows, and active memory summaries; it never offers an identity-key mutation. Private and group conversations remain distinct rows, and where no group title exists the platform conversation ID is shown.

Relationship rows preserve the stored explicit flag, actual `GLOBAL` / `CONVERSATION` / `PRIVATE` scope, provenance distinction, and timestamps. Runtime address resolution keeps the existing precedence: local explicit, global explicit, local inferred, then global inferred. Console mutations require CSRF, restrict edits/forget to explicit terms, use `updated_at` compare-and-set, prevent a duplicate active term in the destination scope, and soft-deactivate terms. Scope edits must bind to an existing conversation when non-global; the registry and SQLite repository remain the write path. The preview endpoint runs the actual resolver against active terms and returns the effective result, candidate priority/source classes, and a coarse reason. Source-message content is not copied to audit. Conversation-scoped entries are keyed by platform conversation ID, matching `AddressResolver` semantics.

The Memory Console has separate administrative FTS queries and retrieval preview. Administrative search applies parameterized type/scope/person/conversation/project/status/time predicates and a bounded page before returning short plain-text previews. `createdFrom` is an ISO-8601 UTC instant inclusive; `createdTo` is exclusive, so queries use `[from,to)` and reject invalid timestamps or `from > to` with 400. Full detail is an explicit authenticated request with `Cache-Control: no-store`; the legacy `/api/memories` projection no longer returns bodies. Manual entries carry `ADMIN_MANUAL` provenance and cannot be edited through this workflow if their source is a platform message. Audit records include actor, ID, type, scope, operation and time, never body or search query. Forget is a soft status transition; the existing FTS triggers remove inactive entries and `MemoryVisibility` excludes them from agent retrieval.

Agent retrieval continues to use `MemoryRetriever` + `RequestContext` + `MemoryVisibility`; the administrative cross-person query is not used for agent context. Retrieval preview constructs a controlled request and calls the real retrieval path only—never an Agent or model provider—and does not persist the preview. The current preview reports included candidates and coarse scope explanations.


## Prompt Management（Phase 4B-3b）

Persona and Simulation are separate editable layers: Persona defines identity/personality/expression; Simulation defines social behavior and tool/memory use guidance. `PromptConsoleService` is the only Console write boundary. It uses the existing `prompt_profiles` and `prompt_versions` store with active version IDs and revision metadata. Every save creates a new immutable version and atomically moves the corresponding active pointer; rollback copies the chosen historical body into another new version. A stale `expectedActiveVersionId` returns 409. History is server-paged and excludes bodies until a version detail/compare request. The 30,000-character limit bounds saved input; token display is an estimate and a warning is shown at high estimated context cost.

Each incoming Agent turn captures both active layers together once through `PromptSnapshotProvider` before model execution. The immutable snapshot is reused for context rebuilds/tool continuations in that turn; changes apply only to later turns. Version IDs are attached to the turn context as metadata. Persisted active pointers and immutable history survive Spring/application restarts. Hard Security Policy has a safe read-only view only; there is no mutation/rollback route. The model envelope places `HardSecurityPolicy` in its own trusted system message before the context system message, whose order is Simulation, Persona, identity/relationship/memory/runtime context, then user input. User-editable text cannot alter server-side capability enforcement.

Prompt responses are `no-store`; content is not logged or copied to audit, and the browser keeps drafts in component memory only. Audit rows contain actor, layer, operation, source/target version IDs and timestamp, never prompt text (including version notes). Chinese and English controls, mobile wrapping, textual added/removed diff markers, and native modal rollback confirmation are part of the same admin surface.

## Social Settings and Model Management（Phase 4B-4a）

`SocialSettingsService` is the only Console mutation boundary for global defaults and per-conversation overrides. It validates stable `QQ:<platform-user-id>` speakers, bounded aliases, probability `0..1`, reply cap `1..8`, outbound rate `1..60/minute`, and multipart gap `0..30s`; CAS revisions reject stale writes with 409. Conversation reads return server-computed `global`, `overrides`, and `effective` maps. Setting an override field to `null` removes that key and resumes inheritance; DELETE clears the whole override. Audit records are per-key and contain only social settings.

The reserved2 runtime captures the effective social settings before trigger evaluation and reuses that immutable snapshot for wake policy, ordinary-message participation, and outbound limits for that accepted turn. Later turns observe hot-applied revisions. WAIT/CLOSED_AGENT/owner-private behavior remains enforced by the existing runtime; manual wake is shown as a capability, not an editable bypass. The current runtime does not implement proactive scheduling or an automatic idle-sleep timer, so the page explicitly marks both unavailable rather than inventing controls. Existing sleep state and question-like trailing punctuation heuristic are described as such.

`ModelProviderConfigService` is the source of truth for both the Models page and the active model adapter. This phase exposes the implemented DeepSeek provider only (DSH is an Agent transport, not an LLM provider), manual model ID, output-token and timeout options. Reasoning effort is explicitly unsupported by the current adapter and rejected by the server. Model configuration/credential changes hot-apply to new turns; `AgentExecutor` captures a provider snapshot once per turn, preserving in-flight model/config identity. Disabled or missing-credential configuration returns a safe unavailable result rather than crashing the runtime.

Credentials are set/replaced/cleared through `SecretStore` and `FileSecretStore`, separate from SQLite config and audit. GET and test responses never return the key and are `no-store`; the browser clears the password field immediately after submission and does not put it in URL or browser storage. The file store uses owner-only permissions and a durable clear tombstone so an environment bootstrap cannot silently restore a cleared key. Provider URL validation permits HTTPS to public destinations; loopback HTTP is restricted to local/test profiles. Unsupported schemes, private/link-local destinations and redirects are rejected, requests have bounded timeouts, and provider bodies/errors are discarded in favor of safe result classes. Connection testing is an explicit minimal live DeepSeek request; all automated browser/backend tests use the deterministic fake tester and send no real provider traffic.

## Stickers, Slang, and Voice capabilities（Phase 4B-4b）

Sticker bytes live under the configured `xingchen.sticker.root` (product default `/data/assets/stickers/`); Windows/test runs set that property to a disposable local directory. `StickerAssetService` is the shared filesystem boundary for recursive scan, upload, metadata, and ID-based preview. Scan is bounded to 200 candidate files and 100 MiB accepted bytes per batch; each file is capped at 10 MiB, raster dimensions at 8192×8192, symbolic links are skipped/rejected, and root/library paths are revalidated before import or preview. PNG, JPEG, GIF and WebP signatures are checked against the filename extension; ImageIO extracts dimensions for PNG/JPEG/GIF, while WebP dimensions/animation remain unknown without a WebP decoder. SHA-256 deduplicates into a managed `library/` copy; importer source files are retained. SQLite stores metadata only (no image BLOBs), and admin search/filter is parameterized and server-paged. Runtime sticker list/search reads the same repository and excludes disabled rows immediately. The OneBot adapter exposes the generic image-segment send operation for these assets, but final format acceptance belongs to the configured gateway. The admin UI deliberately has preview and metadata controls only: there is no admin test-send path because only Agent turns currently enter the safe conversation/outbound-ledger path. UNKNOWN delivery remains at-most-once and is never retried.

Slang remains an offline local dictionary with `CANDIDATE`, `CONFIRMED`, and `REJECTED` states. Only `CONFIRMED` entries are returned by Agent search; status transitions are candidate-only and use updated-time compare-and-set. The authenticated, no-store Console provides paging, text/status/time filters, manual `ADMIN_MANUAL` provenance and bounded meaning edits. Existing evidence is stored as short source/evidence strings, not a structured conversation/actor event record: the UI therefore reports safe source labels and created/updated timestamps rather than inventing actor or message-time metadata. At most three sanitized 140-code-point excerpts are returned; compact audit rows contain term ID, action, old/new status, admin and timestamp, never evidence text. Web research remains disabled and opening the page triggers no network lookup. The legacy authenticated `/api/slang` projection returns confirmed entries only and omits evidence/example bodies.

Voice currently has metadata-only inbound recognition: conversation diagnostics can identify a OneBot `record` segment, but the payload is not stored as an audio asset. No voice send adapter, TTS, transcription, provider setting, voice-specific rate control or safe test-send path exists. The Voice page/API reports these capabilities explicitly as unsupported; it does not fabricate voice style, speaker, speed or emotion settings. There are consequently no voice assets or settings to persist in this phase.

## Usage, Access, Security, Logs, and Operations（Phase 4B-4c）

`UsageConsoleService` is the bounded read/query boundary for the UTC usage ledger. It supports 24h/3d/7d/30d and custom ranges capped at 90 days, paged records (maximum 100), provider/model and conversation dimensions, and daily UTC buckets. The ledger records `prompt_tokens`, cache hit/miss subsets, `completion_tokens`, optional `completion_tokens_details.reasoning_tokens`, provider/model, conversation/turn, timestamp, and duration. Cache categories are subsets of input, reasoning is a subset of output; neither is added twice to total tokens. A migration records whether the provider actually returned a reasoning field; absent fields are explicitly unavailable. Person-level attribution is not in the current ledger, so the Console says it is unavailable rather than allocating a shared conversation turn to every member. Responses contain IDs and numeric/display metadata only, use `no-store`, and never include message, prompt, memory, tool-argument, or hidden reasoning content.

Pricing rows are administrator-entered for an exact provider/model key (one currency per key), per disjoint token class, expressed as currency per 1,000,000 tokens. Currency is three uppercase ASCII letters, not a maintained ISO database. Price updates retain optimistic revision/audit and reject stale writes with 409. There is no effective-date price history or fallback to another model/provider. The ledger's historical `cost` field remains an unused zero placeholder: estimates are calculated at query time using current prices, never immutable invoices.

`UsageCostAccounting` uses BigDecimal throughout; SQLite V27 stores new rates/audit values as nullable decimal TEXT instead of REAL. Migration preserves existing stored rates, revisions and audit IDs, but cannot recover precision previously lost to REAL. Missing nonzero input/cache-hit/cache-miss/output/reasoning rates conservatively mark the whole row UNPRICED with a coarse reason. Zero-token categories need no rate; explicit zero rates are priced zero, never confused with absence of matching pricing. Input/output residual categories exclude their cache/reasoning subsets to avoid double counting.

Summary `cost` reports `costsByCurrency`, global/per-currency counts and tokens, `pricingCoverage` COMPLETE/PARTIAL/NONE, `currencyCount` and `mixedCurrency`. COMPLETE requires at least one usage row and all rows priced; an empty ledger is NONE with zero counts, not a fabricated zero bill. Only single-currency COMPLETE has non-null `estimatedCost` and `currency`; otherwise a safe `totalUnavailableReason` is supplied. Amounts are unformatted base-10 decimal strings (machine-readable, not locale-formatted). Exact currency amounts accumulate before one scale-12 HALF_UP rounding step. Records expose pricing status/reason/currency and nullable estimated amount, plus usage metadata only. A partial record contributes all its count/tokens to unpriced totals, no partial monetary amount.

No FX exists and currencies are never directly summed. The Usage UI shows per-currency priced subtotals, textual coverage and unpriced counts/tokens; mixed and partial warnings can coexist. Only a single fully covered currency displays an estimated total. Changing pricing may change historical estimates. Series and provider/conversation breakdowns are token-only (`metric: TOKENS_ONLY` on breakdown), with no monetary chart or cross-currency cost sorting. Legacy `/api/usage` and `/api/usage/conversations` likewise return `metric: TOKENS_ONLY`, not a summed ledger-placeholder cost. Individually rounded record amounts need not sum to the currency subtotal, which rounds once after exact accumulation. Evidence: `UsageCostAccountingTest` COST-001..015, `DecimalPricingMigrationTest`, `UsageCostSummary.test.tsx`, and `UsageCost.e2e.spec.ts` (USD/CNY/unpriced -> current-price COMPLETE, still no combined total).

`AccessControlService` is the shared source of truth for both the Access page/preview and `SocialRuntime`. Identities are keyed by platform + stable user ID for private rules and platform + conversation ID for group rules; display names are never keys. Configured owner identity is read-only in the page and comes from the existing recovery configuration. Other identities use deny > explicit allow > default deny. Empty rules and evaluation failures fail closed. Preview runs the evaluator only and never invokes a model. Rule writes use an optimistic revision and compact old/new effect audit; message bodies are not captured. Fake-profile runtime tests supply a separate allow-all test double and do not affect production policy.

Security posture is read-only for hard controls: CSRF, BCrypt cost 12, cookie flags, loopback bind, trusted-proxy/public-URL presence, secret-presence booleans, endpoint policy, and active fake/test profile state. Password change requires the current password, a confirmation, and the server-side strength/byte-length rules. Credentials remain BCrypt hashes; bootstrap environment credentials are inserted only while the credential table is empty and never overwrite a rotated password. Each successful app login records the persisted auth generation. Rotation increments it and invalidates this administrator's registered in-memory sessions; subsequent requests against an old generation are rejected. Embedded-container sessions are not persistent across application restart.

Operational logs are a 500-event in-memory ring of enumerated safe authentication/security event codes. It does not accept arbitrary log text, exception strings, filesystem paths, or user content; filters and pages are bounded. This is intentionally a safe event feed, not a replacement for server logging, and its retention is process lifetime only. The immutable audit viewer reads existing audit tables with privacy projections that exclude prompt, message, memory, social-setting values and provider secret values; it returns only actor, time, category, stable target and operation. Operations reports XingChen/JVM/database/Flyway/runtime/integration status only. It has no host process, shell, Docker, filesystem-browse, arbitrary-SQL, restart, or database-maintenance control. Pending reconnect/restart tracking is not implemented and is reported as `UNKNOWN_NOT_TRACKED`; no restart button is shown.

All media tests use generated images under temporary test roots. No user sticker archive or external runtime is accessed. `/api/stickers/{id}/content` is session-authenticated, accepts an ID rather than a path, checks the canonical managed library boundary, emits an allow-listed image MIME, private short hash-based cache headers and `X-Content-Type-Options: nosniff`.
